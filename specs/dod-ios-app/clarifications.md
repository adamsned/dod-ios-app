## Resolved by API research (2026-05-23)

### CL-1 — WPRM recipe data is NOT available as structured JSON via REST
**Question:** Does the WP REST API expose WPRM recipe fields (ingredients, steps, video, times) as structured data?

**Finding:**
- The default `wp/v2/posts` endpoint returns recipe content only as HTML embedded inside `content.rendered`.
- The `wp-recipe-maker/v1` namespace exists but has no public route returning structured recipe JSON. `embed/{id}` returns rendered HTML; `manage/*` requires admin auth.
- The `yoast_head_json.schema` on the API response does **not** include `@type: Recipe`.
- **However:** the rendered post HTML page contains a `<script type="application/ld+json">` block with a full `@type: Recipe` object including `recipeIngredient`, `recipeInstructions`, `prepTime`, `cookTime`, `totalTime`, `recipeYield`, `image`, and `nutrition`. This is highly structured and standardized.

**Resolution:** **Hybrid fetch strategy.**
1. Recipe **list** screens (home feed, category, search results, related, saved) use the WP REST API. Cheap, paginated, JSON.
2. Recipe **detail** screens fetch the rendered HTML page (`post.link`) and parse the JSON-LD `Recipe` block to get structured ingredients/instructions/times/nutrition.
3. The JSON-LD parse is the single source of truth for recipe body content. WPRM HTML scraping is **not** allowed as a primary path (constitution §4 already bans HTML scraping as primary).

**Acceptance criteria impact:**
- **AC-4.1 / AC-4.3 / AC-4.6:** times, ingredients, instructions sourced from JSON-LD.
- New **AC-4.11** to add: recipes without a parseable `Recipe` JSON-LD block must not appear in feed/search/category lists; they're filtered server-side... wait, the WP API can't filter on this. Filtered client-side after detail-fetch. See CL-9 below.

### CL-2 — Pagination
**Question:** What's the WP REST API per-page cap?
**Resolution:** WordPress default max is `per_page=100`. We use **`per_page=20`** for all list fetches (matches AC-1.2 batch size). Server may return fewer when fewer remain.

### CL-3 — Categories vs Tags
**Question:** Does "category" mean WP categories, tags, or both?
**Resolution:** **WP categories only** in v1. Sample post showed 2 categories, 0 tags. Tags are not populated on this site. Revisit if blog adds tag usage post-launch.

**Acceptance criteria impact:** AC-2.1 — "all WordPress categories" stays as written.

### CL-4 — Canonical recipe URL
**Question:** What URL goes in the share sheet?
**Resolution:** Use `post.link` verbatim. Confirmed hostname is `www.dutchovendaddy.com` (not bare `dutchovendaddy.com`). Don't rewrite or normalize.

**Acceptance criteria impact:** AC-6.2 — share payload is exactly `post.link`.

## Phase 10 amendments (2026-05-24)

- **CL-34 (US-20, 2026-05-24)** — Search filter chip iconography: `tag.fill` over `tag`, `number`, `crop.rotate`, or keeping `folder`. **Why `tag.fill`:** WordPress categories are taxonomy terms (CL-3 — the blog's "Categories vs Tags" decision treats both as filterable taxonomies; the app surfaces only categories in v1 but the semantic is "filter by taxonomy"). `tag.fill` is the iOS-stock glyph for that semantic — Reminders uses it on its tag filter pills, Files uses it in the tag column header, and Photos uses it on the people-and-pets tag chips. The `.fill` variant matches the chip's selected-state convention: the chip already toggles a filled cast-iron-brown capsule when a category is picked, so a filled glyph reads as "this chip is a filter primitive" even in its idle unselected state. Considered: outline `tag` — rejected because the surrounding chip glyphs (`clock`, `clock.arrow.circlepath`) are visually weighted as solid line drawings; a thin outline `tag` would look anemic next to them at the 13-pt caption rendering size. Considered: `number` — rejected because `number` reads as "ordinal / count," not as "filter by name." Considered: `crop.rotate` (the WP admin tag editor uses something like it) — rejected as obscure; nobody outside the WP admin recognizes that glyph. Considered: keeping `folder` and only changing the empty-state glyph — rejected because the empty state's `questionmark.folder` is correctly read as "thing-not-found in a search context" (the `?` carries the meaning, not the folder); the live bug is on the chip, not on the empty state. Implementing PR: T-350 / [#23](https://github.com/adamsned/dod-ios-app/pull/23).

- **CL-35 (US-21, 2026-05-24)** — **Widget image bridge: file-export to App Group container.** The featured widget (US-9) and the saved-recipes widget (US-17 / T-322) both currently render a placeholder glyph in place of the recipe hero image. The root cause T-322's agent flagged: *"The existing `CachedImage` SwiftData store keeps bytes in SwiftData, not filenames in the App Group container. The widget extension renders a placeholder for nil filenames per AC-17.5."* The widget extension cannot reach the host app's SwiftData store (separate processes, separate sandboxes — App Group sharing covers UserDefaults + files but not SwiftData containers without a custom container URL), and constitution §9 implicit + AC-17.6 forbid widget-side network fetches. Three options considered:

  1. **File-export bridge (chosen).** When the host caches image bytes via `RecipeStore.cacheImage(url:bytes:...)`, also write the bytes to a file inside the shared App Group container under a deterministic filename derived from the URL (SHA256 + extension preserved). The snapshot wire format carries the filename; the widget reads the file via `FileManager.default.containerURL(forSecurityApplicationGroupIdentifier:)`. Eviction stays write-through — `evictImagesIfNeeded()` deletes both the SwiftData row and the file. **Cost:** ~2× storage for images that get cached (200 MB SwiftData cap + same bytes on disk under the App Group). Widget code stays simple — read a file, hand the URL to `AsyncImage`, done. **Why this wins:** the saved-recipes widget already half-implemented this pattern in T-321/T-322 — `SavedRecipesWidgetSnapshot.Entry.heroImageFilename` already exists, and the widget already calls `containerURL(forSecurityApplicationGroupIdentifier:)` + appends the filename. The host side is the missing half. Bias-toward-Option-A from the task prompt; investigation confirmed the saved widget was already on this track.
  2. **Shared SwiftData container.** Move the `CachedImage` SwiftData store into the App Group container so the widget extension can `open` it directly. Single source of truth; no 2× storage. **Why rejected:** SwiftData container opens are heavy (10–50ms even for a small store) and the widget timeline provider is called frequently. The widget process would need to migrate the schema on first open if the host hasn't bumped it yet (Schema V3 today). Concurrent writes from host + opportunistic reads from widget would also need write-protection — SwiftData's `ModelContainer` is not designed for cross-process readers and "careful concurrency" handwaving here is risky for a widget surface where a crash means a blank tile on the user's home screen. Option A trades ~200 MB of disk (worst case, never hit in practice — see CL-35.2 below) for a much simpler concurrency story.
  3. **URLSession in the widget.** Widget extension fetches the image directly from the WP CDN. **Why rejected:** AC-17.6 wording ("No network calls from the widget extension itself") and constitution §9 implicit (no background network if avoidable) both forbid this. The featured widget has the same shape so the same constraint applies — there's no "this widget can but that widget can't" carve-out worth introducing.

  **CL-35.2 — Storage worst-case:** the bridge writes a file for *every* image bytes cached, not just those needed by the widget. For the featured widget today that means the top-5 feed-entry hero images (CL-9 says max 5 entries in `WidgetSnapshot`). For the saved widget that means up to 3 saved-recipe hero images (CL-26 says max 3). Generally only ~8 files exist concurrently. The 200 MB image cache cap (NFR-2) already bounds the SwiftData store; mirroring it as files yields ~200 MB more on disk in the absolute worst case, far below any iPhone storage warning threshold. No mitigation needed in v1; revisit if usage data later shows a problem.

  **CL-35.3 — Eviction ordering:** the bridge deletes the file inside the same `evictImagesIfNeeded()` SwiftData transaction that deletes the row. If the file delete fails (file already gone, container vanished, etc.) the SwiftData delete still succeeds — the file delete is best-effort. Both directions ("row exists but file gone" and "file exists but row gone") are gracefully handled by the readers: the widget renders the gradient placeholder when the file is missing, and the host's `image(url:)` accessor only consults SwiftData so a stale file is invisible.

  **Implementing PR:** T-360 / `feat/T-360-latest-recipe-widget`. PR diff is bounded to `Packages/DODPersistence/Sources/DODPersistence/RecipeStore.swift` (write/evict hooks), a new `Packages/DODSupport/Sources/DODSupport/WidgetImageBridge.swift` (filename derivation + container URL resolver — shared by host + widget), `Packages/DODFeatureFeed/Sources/DODFeatureFeed/FeedDependencies.swift` (snapshot now carries `heroImageFilename`), `Widget/FeaturedRecipeWidgetEntryView.swift` (resolve filename to `file://`), plus widget snapshot wire-format additive bump and tests in `Packages/DODSupport/Tests/` + `Packages/DODPersistence/Tests/`.

- **CL-37 (US-22, 2026-05-24)** — Lock-screen widget family scope: **`.accessoryRectangular` only.** Apple's `WidgetFamily` exposes three lock-screen-eligible families on iOS 16+: `.accessoryRectangular` (multi-line, ~170×72pt tall enough for a title + one body line), `.accessoryCircular` (round, very small — built for single glyphs / step counters / battery-style readouts), and `.accessoryInline` (a single line of text rendered alongside the clock/date glyphs at the top of the Lock Screen). The backlog entry asked specifically for a "rectangular-family lock-screen widget"; this CL formalizes that and explains why the other two are not in scope. **Why rectangular:** the latest-recipe surface needs to show *both* a title and a short description, and the user must be able to identify a recipe at a glance — the title alone in `.accessoryInline` doesn't carry enough context ("Bourbon Berry Cake" is fine; "Recipe With Three Things" is meaningless), and a `.accessoryCircular` surface forces a glyph-only treatment that has no good answer for "what recipe?" because recipes don't have brand glyphs. **Why not `.accessoryCircular`:** a useful circular surface needs a 1–2 character payload or a single icon. The featured-recipe widget data (title + excerpt) doesn't fit either. We'd ship a knife-and-fork glyph that means nothing — which is exactly the placeholder anti-pattern we already removed from the home-screen widget. **Why not `.accessoryInline`:** the inline family is shared between every inline widget the user has installed (weather, battery, calendar event, etc.) — it cycles through them and is rate-limited by the system. - **CL-52 (US-31 / T-440, 2026-05-26)** — **Recipe scaling: fraction-rendering precision (eighth-cup canonical set, 1/16 snap tolerance), warning threshold rationale (>12 servings on a 5-quart home dutch oven), and the `FractionRenderer`-in-`DODSupport` decision (two consumers: recipe detail view + Cook Mode drawer).** Round-3 backlog "Recipe scaling" entry (dad's idea, sized S) calls for tapping a "Serves N" stepper and watching ingredient quantities re-render with cook-friendly fractions. This CL captures three decisions the implementer must lock before the source change lands.

  **Decision 1: Canonical fraction set = `{1/8, 1/4, 1/3, 1/2, 2/3, 3/4, 7/8}` + whole numbers.** **Why these seven and not others:** these are the cook-grade fractions every measuring spoon + measuring cup set in a US kitchen actually carries. A 1/8 tsp + 1/4 tsp + 1/2 tsp + 1 tsp set covers spoon-level dosing; a 1/4 cup + 1/3 cup + 1/2 cup + 1 cup set covers cup-level. The 2/3 cup and 3/4 cup are the only "between" cup measures that show up on standard sets (e.g. Pyrex, OXO, KitchenAid). 7/8 cup is a stretch — most sets don't carry it — but it's included because the snap distance from 3/4 cup (0.75) to a full cup (1.0) is large enough (0.25) that a scaled-up 7/8 result wants a closer rendering than "0.88 cup". 5/8 and 3/8 are NOT in the set because they would crowd 1/2 and 2/3, which are the dominant "middle" measures — keeping fewer canonical fractions means more values snap to common spoon/cup measures rather than the kitchen-junk-drawer ones. **Why integers as a separate render branch:** "2 cups" vs "2 0/8 cups" (or worse, "2.0 cups") — the integer-only render is the cook's expected default. The `renderQuantity(_:)` function checks `whole + remainder` separately and never emits an "X 0/Y" string.
  
  **Decision 2: Snap tolerance = 1/16 (= 0.0625).** **Why 1/16:** that's the half-distance between successive 1/8 increments. A remainder within 1/16 of a canonical value snaps to it; anything outside falls into the next-nearest canonical band. The math: `0` ↔ `1/8` mid = 0.0625, `1/8` ↔ `1/4` mid = 0.1875, `1/4` ↔ `1/3` mid = 0.2917, `1/3` ↔ `1/2` mid = 0.4167, `1/2` ↔ `2/3` mid = 0.5833, `2/3` ↔ `3/4` mid = 0.7083, `3/4` ↔ `7/8` mid = 0.8125, `7/8` ↔ `1` mid = 0.9375. Within those bands, every value snaps to the closest canonical. The mid-distance bands are uneven (1/3 sits closer to 1/4 than to 1/2) — which is the whole point: a `0.34` remainder snaps to `1/3` rather than `1/2` because 1/3 is its physical neighbor on the measuring-spoon side. **Why not 1/32:** would force more values to fall into the decimal-fallback branch, which renders as e.g. `"0.13"` — readable, but not what a cook expects. 1/16 is the largest tolerance that doesn't merge two adjacent canonical fractions into one band. **Why not adaptive per-fraction tolerance:** the canonical set is dense enough that a flat 1/16 tolerance keeps the mid-distance math symmetric; adaptive tolerance would invite "this should round to X but I expected Y" arguments that the spec can't pre-empt.
  
  **Decision 3: `FractionRenderer` lives in `Packages/DODSupport`, not in `DODFeatureRecipeDetail`.** **Why:** Cook Mode's ingredients drawer (`CookModeView.ingredientsDrawer`, declared in `Packages/DODFeatureRecipeDetail/Sources/DODFeatureRecipeDetail/CookModeView.swift`) renders the same ingredient rows the detail screen does. If the user scales to 8 servings on the detail screen and then taps "Cook Now," the drawer must show the same scaled quantities — otherwise the user gets two different ingredient lists for the same cook. The renderer needs to be importable from both surfaces. Putting it in `DODSupport` (the existing home for `StepTimerParser`, `HTMLSanitizer`, `WidgetImageBridge` — pure utility code) means both view layers consume one canonical fraction table. The L1 test suite for the renderer lives in `Packages/DODSupport/Tests/DODSupportTests/FractionRendererTests.swift` per the constitution §6 L1 mandate ("every view model, networking type, and domain transform" gets a unit test home). **Why not embed the renderer in `DODFeatureRecipeDetail`:** would force `CookModeView` to import it via the same module (it does), but it would also force any future consumer (a hypothetical share-sheet export, a future widget surface that wants to render scaled quantities, a future Spotlight indexer) to take a dependency on the feature package — which violates the constitutional dependency direction (features depend on support, never the reverse).
  
  **Decision 4: Warning threshold = 12 servings on a 5-quart home dutch oven.** **Why 12 and not 8 or 16:** five-quart is the most common home-cook size on Lodge's and Le Creuset's catalogs (the brand's "Dutch Oven Daddy" identity already orbits Lodge cast iron at this size). A typical stew, chili, or braise renders at roughly 1.5 cups per serving = 0.4 quarts per serving. A 5-quart pot at 80% fill (the practical max — anything more risks overflow during simmer) = 4 quarts of usable volume = ~10 servings. 12 is the just-past-the-comfortable-cap number that warrants a "you should consider two batches" caption. The threshold is a soft signal — the math at 13 servings still works, it's just that the cook should know they're scaling past what their pot can physically hold. **Why a caption and not a confirmation alert:** the user knows their kitchen; the app shouldn't gate. A non-blocking caption ("Most home dutch ovens cap out around 12 servings. Consider doubling the recipe in two batches instead.") with an `exclamationmark.triangle.fill` glyph in `DODColor.burntOrange` conveys the constraint without disabling the stepper. **Threshold encapsulation:** the constant `FractionRenderer.dutchOvenServingWarningThreshold = 12` and the helper `FractionRenderer.shouldShowDutchOvenWarning(forServings:)` live in `DODSupport` so the view-model gate and the view's render condition use the same number — future tuning lives in one place. **Why not threshold by recipe category:** the spec doesn't carry pot-size metadata per recipe; a chili and a stew both nominally cook in a 5-quart, but the densities differ. The 12-serving threshold is a generic warning that triggers for *every* recipe — false-positive-friendly is the correct bias because the caption is informational, not blocking.
  
  **Decision 5: Source `Recipe` is never mutated; scaling is pure presentation.** **Why:** the source recipe is the contract with the JSON-LD parse (per AC-4.11). Mutating `Recipe.servings` or `RecipeIngredient.text` would taint the cache (`RecipeStore.cache(detail:)`), the widget snapshot (the saved-widget publisher reads `Recipe.title` and could read `servings` if a future widget surface wanted it), and the Cook Mode drawer (which takes a `Recipe` directly, not a scaled view-model projection). The view layer multiplies at render time inside `RecipeDetailView.ingredientsSection`'s `ForEach` body via `FractionRenderer.scale(ingredient.text, by: viewModel.servingsScaleFactor)` and passes the result as `IngredientCheckRow.displayText`; `ingredient.text` (the source string) is left untouched, and `IngredientCheckRow.accessibilityLabel` reads from `displayText` so VoiceOver announces the scaled quantity. **Why not store the scale on `Recipe` as a transient field:** the `@Model` `CachedRecipe` SwiftData type would need a new column, and the in-memory `Recipe` value type would need a property that's nil for every code path except the recipe-detail render — adds shape complexity for what's already cleanly solved by a view-model `userServings` integer and a derived `servingsScaleFactor` Double. **Why not persist `userServings` across app launches:** out of scope for v1. The backlog entry doesn't ask for it ("pure presentation logic; no schema change since the source recipe is untouched"). If a v1.x user-test session surfaces a "I scale every batch to 8" pattern, that's a clean follow-up that adds a `lastScaledServings` `UserDefaults` key keyed by recipe id — but the v1 path stays scale-resets-on-screen-exit.
  
  **Decision 6: Stepper range = 1...24.** **Why upper bound 24:** the warning threshold is 12. The stepper needs to reach past it so the warning gets exercised (you can't see the caption if you can't get to 13). Doubling the warning threshold (24) gives the user enough headroom to scale a 4-serving recipe up to 6× (24 / 4) — which is the upper end of "I'm hosting a small dinner party" usage. Higher than 24 is the "doing a catering job" tier that doesn't fit the single-stepper UI anyway (the cook is doing more spreadsheet math than recipe-app math). **Why lower bound 1:** a single serving is the floor. Zero servings is meaningless (and would force every quantity to zero, an unproductive output); negative servings are obviously invalid. Both ends are clamped at the view-model layer via `setUserServings(_:)` so any programmatic set is correct by construction. **Why a stepper and not a slider:** integer values, the user needs to land on exact counts (you don't host a party for "between 6 and 7 people"), and the stepper's `−` / `+` controls map directly to the "I want one more / one fewer" intent. A slider would invite imprecision and require a label readout that's effectively the same as the stepper's current value display anyway.
  
  **Decision 7: Ingredient parser walks the head of `RecipeIngredient.text`; no structured amount/unit decomposition.** **Why:** the JSON-LD `recipeIngredient` payload from WPRM is a single string per ingredient with quantity + unit + name interleaved (`"720 g bread flour"`, `"1 1/2 pounds cod fillets (cut into 2-3 inch uniform chunks)"`, `"Salt and freshly ground black pepper (to taste)"`, `"melted butter (for dipping)"`). There is no structured `amount` + `unit` + `name` decomposition to lean on — that's a recipe-data-source contract decision baked into CL-1 (JSON-LD parse from the rendered post page, not a structured WP REST endpoint). The renderer walks the head of the string looking for, in precedence order: a mixed number (`"1 1/2"` or `"2 ½"`), a decimal (`"1.5"`), a fraction (Unicode `"½"` or ASCII `"1/2"`), or a plain integer (`"4"`). The first match wins; everything from the first non-quantity character to the end is appended verbatim to the rendered quantity (with a single normalizing space between). Lines that don't begin with a digit or a Unicode vulgar fraction return verbatim — the renderer never invents a quantity, so `"Salt and freshly ground black pepper (to taste)"` stays correct at any scale. **Why not parse units too (e.g. "cup" / "tablespoon"):** unit normalization is a separate problem (gram-to-cup conversion, oz-to-tbsp conversion, plural vs singular agreement) that the spec doesn't tackle. The renderer rewrites the quantity; the unit string travels untouched. **Why not handle "and" glue ("1 cup and 2 tablespoons"):** the leading-quantity-only parse is sufficient for the common case — multi-quantity ingredients are rare in WPRM-published recipes (the canonical pattern is one quantity per line). If user testing surfaces a pattern of multi-quantity lines that scale wrong, that's a clean follow-up — but the v1 spec doesn't carry it.

- **CL-50 (US-1 / T-510, 2026-05-26)** — **New-recipe surfacing: WP REST responses are served from `URLCache.shared` (and Cloudflare's CDN) without a `Cache-Control` directive, so `WPRestClient.posts()` can return a stale page-1 batch that omits a just-published recipe.** Root cause traced by the round-6 backlog "New-recipe surfacing" entry: T-420's REG-16 nightly L2 test (`LiveAPITests.newestPostIsReachableViaFeedRefresh`) passes in isolation — one fresh HTTP call inside a clean test process returns the newest post id and the round-trip through `WPRestClient.posts()` → `RecipeStore.cache(listItems:)` → `RecipeStore.listItems(forIDs:)` surfaces it. But in production the user keeps the app foregrounded across multiple refreshes, and `WPRestClient.get(...)` builds its `URLRequest` with the default `cachePolicy = .useProtocolCachePolicy` and no explicit `Cache-Control` request header. Two consequences stack: (a) **iOS URLCache.shared.** `URLSession.shared` consults its global cache before hitting the network; the WP REST response carries `Last-Modified` but **no `Cache-Control` or `Expires`**, so URLSession applies HTTP heuristic freshness — typically `0.1 * (now - Last-Modified)` — and returns the cached payload within that window. With a CDN-cached origin response showing `Age: 225` and `Last-Modified` 5 minutes old, the heuristic window is ~30 seconds during which pull-to-refresh returns the same 20 IDs the previous refresh just saw. (b) **Cloudflare CDN.** `cf-cache-status: HIT` confirms `dutchovendaddy.com`'s WP REST endpoint sits behind Cloudflare's CDN with a multi-minute edge TTL (the `x-wp-cf-super-cache-disabled-reason: API Request` header confirms WP's own super-cache is bypassed, but Cloudflare's edge cache is independent and active). Even when iOS URLCache misses, the CDN can serve a stale edge copy that predates a just-published recipe — the user pulls to refresh, the request leaves the device, the CDN returns the same pre-publish JSON, and the newest post stays invisible until Cloudflare's edge TTL expires. **Why T-420's L2 test missed this:** the test runs in a fresh `swift test` process where `URLCache.shared` is empty, makes one fresh call, and the response naturally bypasses both caches because there's no prior entry to serve. The CDN side gets touched by exactly one request, so any edge-cache staleness is statistically unlikely on a single run. The bug only surfaces under the *production* call pattern: user-driven refreshes within seconds-to-minutes of each other against a Cloudflare-cached endpoint. **Fix (REG-18):** set two markers on the `URLRequest` `WPRestClient.get(path:queryItems:)` constructs before handing it to `httpClient.data(for:)`: `request.cachePolicy = .reloadIgnoringLocalCacheData` (forces URLSession to skip URLCache.shared and hit the network) AND `request.setValue("no-cache", forHTTPHeaderField: "Cache-Control")` (asks Cloudflare to revalidate with origin per RFC 7234 §5.2.1.4). Both lines are required: cachePolicy alone bypasses iOS URLCache but lets the CDN serve a stale edge copy; `Cache-Control: no-cache` alone tells the CDN to revalidate but leaves URLCache.shared serving stale entries on the device side. The two-line fix forces both layers to revalidate, so pull-to-refresh actually picks up newly-published recipes. The change lives in `WPRestClient.get(path:queryItems:)` (the shared helper that backs `posts()`, `categories()`, `search()`, `comments()`, `ratings()` — every WP REST call this app makes), so all WP REST surfaces benefit identically. The WP REST payloads are small JSON (<50KB) and the app makes maybe a dozen REST calls per session, so the bandwidth/latency cost of bypassing both caches is negligible compared to the user-visible cost of the feed missing a freshly-published recipe. **Why bypass cache on every call rather than only on pull-to-refresh:** the alternative would be to expose a `forceFresh: Bool` parameter on `WPRestClient.posts()` and have `FeedViewModel.refresh()` set it. Rejected — that pushes the cache-control decision up to the call site and invites the same bug shape in any *future* call site that forgets to set it (e.g., a categories-refresh flow, a search-results refresh, a pull-to-refresh on the Saved tab). The constitution §6 "test pyramid" mandate to lock regressions at the lowest seam they can be locked at applies: bypass at the HTTP client level is the lowest seam that makes every call site correct by construction. **Why not also opt-in to `URLRequest.cachePolicy = .reloadIgnoringLocalAndRemoteCacheData`:** that policy adds `Pragma: no-cache` on top of `Cache-Control: no-cache`. Cloudflare honors both; `Pragma` is the HTTP/1.0 equivalent and adds no signal Cloudflare doesn't already get from `Cache-Control`. Sticking with `.reloadIgnoringLocalCacheData` + the explicit `Cache-Control` header keeps the request shape readable in `Charles` / `mitmproxy` traces (one header, one cache directive) without changing observable behavior. **Why not just add a cache-busting query parameter (e.g., `_t=<unix-ms>`):** that would force a CDN miss too (verified — `curl '...?_t=12345'` returns `cf-cache-status: MISS` and a fresh response from origin), but it pollutes Cloudflare's cache with a unique key per request and defeats the CDN's value for everyone hitting the same origin. The `Cache-Control: no-cache` header tells the CDN to revalidate this specific request with origin while still using the same cache key — keeps the CDN useful for non-app HTTP clients that don't opt out. **Why not `cachePolicy = .reloadRevalidatingCacheData`:** that policy tells URLSession to revalidate the cached entry with the server via `If-Modified-Since` rather than refetching unconditionally. The WP REST response carries `Last-Modified` but the server's revalidation response (`304 Not Modified`) would still come from Cloudflare's edge cache, not origin — same staleness problem. `.reloadIgnoringLocalCacheData` plus the request header forces a network round-trip that Cloudflare specifically routes to origin. **What CL-50 does NOT touch:** `WPRestClient`'s decoder shape (no change to JSON decoding), the `WPDTO` family (no change to wire-format parsing), `RecipeStore.cache(listItem:)` / `RecipeStore.listItems(forIDs:)` (the store-side path was already correct — the L2 test proved it on every nightly run since T-420 merged), `FeedViewModel.loadInitial(forceReplace:)` / `FeedViewModel.refresh()` (the view-model code was already correct), the blocklist clearing path (`AC-1.7` semantics unchanged), the offline-cache hydration path (`hydratedFromCache()` still returns nil per T-091/T-101 punt), or the `LiveFeedDependencies` widget-snapshot publish hook (CL-45's T-362 prefetch is unaffected — image bytes still arrive via `ImageLoader` + `RecipeStore.cacheImage(url:bytes:)`, and those `ImageLoader` calls hit `dod.shared`'s CDN image cache where edge caching is *desirable* and stays in place). **What CL-50 ADDS to AC-T4:** REG-18 — a regression test that fails on `origin/main` (URLCache.shared serves a planted stale response) and passes after the fix (URLCache is bypassed, fresh network data returned). Sighted users learn the affordance after one tap. **Why honor Spencer's direction:** the request is explicit, the trade-off is small (one tap to learn), and the convention is at least defensible as "the icon names the current state" rather than "the icon names the destination." - **CL-67 (US-39 / T-681, 2026-05-27)** — **Aisle classifier strategy: ship a static keyword map for v1 (~80 entries hand-curated from a US grocery-store walk), with a documented escalation path to (b) ingredient-tagged dictionary if the `Aisle.other` share of `shoppingListItemAdded` events crosses a documented threshold.** The Shopping List feature classifies each ingredient line (e.g. `"2 cups diced yellow onion"`, `"1 tsp smoked paprika"`, `"1 lb ground beef, 80/20"`) into a coarse-grained `Aisle` enum (~9 cases: produce, dairy, meatSeafood, bakery, frozen, pantry, spices, beverages, other). The classifier is the only piece of the Shopping List that has a real algorithmic decision under it — every other surface is plumbing. **Four candidate strategies for v1:** **(a) Static keyword map** — a ~80-entry `[String: Aisle]` table mapping known ingredient stems ("onion" → produce, "milk" → dairy, "paprika" → spices, "ground beef" → meatSeafood, "vanilla extract" → pantry) plus the fallback rule `default → .other`. The classifier tokenizes the ingredient line (lowercase, drop quantity + unit prefix via a small regex `^\s*[\d¼½¾⅓⅔⅛⅜⅝⅞/.\s-]*(cups?|tsps?|tbsps?|oz|lbs?|grams?|g|ml|l|cloves?|sprigs?|cans?|packages?|pkgs?)?\s*`, drop trailing comma-separated qualifiers via `,.*$` split), then looks up each remaining whitespace-separated token against the keyword map and returns the first match (or `.other` if no match). **(b) Ingredient-tagged dictionary** — every ingredient line gets pre-tagged at the JSON-LD parse step (extend `RecipeIngredient` with an optional `aisle: Aisle?` field populated by a richer parser that handles compound terms like "all-purpose flour", "extra virgin olive oil", "boneless skinless chicken thighs" via a multi-token longest-prefix match against a ~200-entry dictionary). The classifier becomes a no-op pass-through when the field is populated. **(c) Hybrid** — try (a) first; on `.other`, fall through to a longer-form fuzzy matcher (Levenshtein distance ≤ 2 against the canonical-name table for known typos: "yelow onion" → "yellow onion" → produce). **(d) WP-side classification** — extend the WordPress backend so every published recipe carries an `aisle` post-meta per ingredient via a WPRM plugin or a custom REST namespace; the app reads the pre-classified value, the classifier is empty on-device. **Decision: ship (a) — the static keyword map — for v1.** **Why (a) and not (b):** (b) requires editing the JSON-LD parse path (every ingredient line gets a richer parser), changes the on-disk Codable shape of `RecipeIngredient` (a new optional `aisle` field) which forces a back-compat decode branch for older cached recipes, adds a new domain-level decision (where does the longest-prefix-match dictionary live? is it bundled with the app or fetched at first launch? what's the update path?), and is fundamentally a v1.x scope: it's the right answer once we have telemetry showing the static map's miss rate is too high. Until that signal exists, (b) is YAGNI. **Why (a) and not (c):** the fuzzy matcher in (c) is a flashing-warning-light pattern — fuzzy matching with Levenshtein on cooking ingredients introduces false positives ("rye flour" vs "rice flour" are one edit apart but route to different aisles in a real grocery store: rye to bakery, rice to pantry; the v1 static map handles both correctly as exact matches but the fuzzy path could flip them). Building a fuzzy matcher costs the same as building (b)'s richer dictionary but produces a worse result. Strike (c). **Why (a) and not (d):** (d) requires a WordPress-side change Spencer + dad haven't authorized, requires a constitution amendment §4 (the v1 app is "mostly read-only" and an aisle-classified ingredient would be a new write surface on the blog side even if not the app side), and bottlenecks aisle accuracy on Ned's content-author workflow rather than on the v1 app's release. Strike (d). **Escalation trigger for (a) → (b):** the `shoppingListItemAdded(recipeID:aisle:)` event per AC-39.10 records the classifier's output for every row inserted. If the share of `.other` rows exceeds **15%** of all inserted rows over a rolling 30-day window — the documented threshold below which the v1 classifier is "good enough" per the keyword-map design intent — that's the signal to plan (b). A separate task captures the dictionary build, the JSON-LD parse extension, the back-compat decode, and the deprecation of the on-device keyword map. The 15% threshold is a starting calibration; dad's actual cooking is the ground truth and we'll adjust on the first 30-day report. **Why ~80 entries and not 50 or 200:** 50 is too thin (drops common items like "yogurt", "ground turkey", "tomato paste"); 200 is the (b) dictionary size and the build cost crosses the YAGNI threshold for v1; ~80 covers every entry on the dad-tested DOD recipe corpus (sampled by walking the public dutchovendaddy.com recipe list and tokenizing the JSON-LD `recipeIngredient` arrays of the ~50 highest-traffic posts). **What the keyword map looks like:** the keyword map ships as a `String -> Aisle` static dictionary literal in `Packages/DODSupport/Sources/DODSupport/IngredientAisleClassifier.swift` (NOT as a JSON resource — the cost of a resource load + parse + cache vs. a static dictionary literal that the Swift compiler turns into a constant is not worth the extra moving part; the dictionary is small and human-readable in source). Building a robust Swift parser is a multi-week task in itself, gates the v1 ship, and produces a result that's still wrong on enough edge cases that the user will see "6.25 cups onion" rendered as "6 ¼ cups" without understanding the conversion. **Why (a) and not (b):** even same-unit summation requires the quantity-prefix regex to handle fractions correctly (`½ cup + ½ cup = 1 cup` — easy; `½ cup + ¼ cup = ¾ cup` — needs fraction arithmetic; `1 ½ cups + ½ cup = 2 cups` — needs mixed-number normalization). Once you've written that, you've built half of (c)'s normalization anyway, but you're still wrong on the descriptor-as-count edge cases ("1 medium onion + 1 medium onion = 2 medium onions" is correct but the user probably wanted "2 medium onions" formatted as "2 onions"). The user's mental model is "I'm at the store, here are the things I need from this aisle"; per-recipe rows with the recipe-title sub-label match that mental model better than fragile arithmetic, because the user can see "I need onion for two recipes" and decide for themselves how much onion to buy. **Why (a) and not (c):** (c) is (b) plus a density-aware unit converter for volume-to-weight conversions ("1 cup flour" → 120g; "1 cup butter" → 227g). The conversion tables are ingredient-specific and the source-of-truth data isn't bundled with iOS; we'd need a dependency or our own table. Strike (c) hard. **Why (a) and not (d):** quantity-string concatenation produces visually ugly output ("2 cups + 1 cup + ½ cup diced yellow onion") that's worse than three clean rows; the user gets neither the convenience of a single computed number nor the clarity of separate rows. Strike (d). **What per-recipe rows look like in the rendered list:** each row shows the original ingredient text (verbatim from `RecipeIngredient.text`) followed by a small dimmer sub-label `(<recipe title>)` per AC-39.2. Three "diced yellow onion" entries from three recipes render as three Produce-aisle rows, each with a different recipe title in parens. This is a feature, not a bug — the user can mentally roll up the quantities at the store ("OK, three recipes call for onion — I'll grab two big yellow onions and call it good"). **Why the recipe-title sub-label is load-bearing:** without it, three identical "diced yellow onion" rows in Produce look like a bug ("why is onion showing three times?"). With the sub-label the user understands the multiplication source. **Activation trigger for (a) → (b)/(c):** the deferral graduates when (i) the v1 list ships AND (ii) the static aisle classifier graduates to (b) per CL-67 (because the tagged-ingredient dictionary surfaces a canonical-name pass that quantity merging needs to identify same-ingredient rows), AND (iii) the user signal emerges ("I wish my onion entries combined"). Without all three, the v1 per-recipe rendering is the right answer. The Swift-side libraries to audit when this graduates: `Apple Foundation Measurement` (handles unit conversions for distance / mass / volume but not ingredient-density conversions), `swift-fraction` or similar (no canonical choice; the constitution §3 "default answer is no new dependency" applies — the activation task likely re-implements fraction arithmetic in pure Swift). **Considered:** ship (a) but render the rows in an alphabetical-within-aisle order so duplicates visually cluster. Rejected — alphabetical-within-aisle is already what AC-39.4 says (the per-aisle order is sub-sorted by `addedAt` descending so the most recently added rows surface at the top; if dad adds three recipes in a row and they each call for onion, those three onion rows naturally cluster because they were added at adjacent timestamps). The user gets the visual cluster effect for free without a sort-key change. **Considered:** show a roll-up at the bottom of each aisle section ("3 onion entries"). Rejected — adds rendering complexity for marginal value; the visual cluster of three rows is the rollup. **Spec/trace:** US-39 / AC-39.2 (insert per ingredient, one row per source), AC-39.4 (aisle rendering with the per-recipe rows), AC-39.5 (per-row toggle). Implementing PR: T-682 (persistence) + T-684 (rendering).

A SwiftData `@Relationship` to `CachedRecipe` would (a) couple the shopping-list row's lifecycle to the cached-recipe row (deletion cascade rules become a real design call), (b) require a fetch-with-relationship path in the view model, (c) re-introduce the eviction trap from (b) above — if `CachedRecipe` is LRU-evicted, the relationship snaps. The `.other` fallback in the computed accessor is defensive — a future schema rollback could leave a row with an `aisleRaw` string the current `Aisle` enum doesn't recognize, and routing it to `.other` is safer than crashing. **Migration test:** T-682 ships an L1 test `MigrationV4Tests.V3_to_V4_lightweightMigration` that opens a SchemaV3 container, inserts a `CachedRecipe` + a `CachedListPage` + a `CachedImage`, closes it, re-opens at SchemaV4, asserts (i) every V3 row is intact and queryable, (ii) the new `ShoppingListItem` entity exists and is empty, and (iii) an insertion of a `ShoppingListItem` round-trips through `try modelContext.save()`. Reusing `ingredientsJSON` (the cached JSON-LD ingredient blob) as a generic text-body slot was rejected by CL-63 for article bodies; the same anti-pattern applies here. Rejected — YAGNI; the v1 schema is single-list-implicit, the future migration (adding the parent and back-filling every existing row into a system-default list) is bounded and additive. **Considered:** store the `Aisle` enum as a SwiftData `@Attribute(.transformable)` value. Rejected — adds an `NSSecureCoding` requirement on `Aisle` and serializes to a `Data` blob, which is opaque vs. the string raw-value (you can inspect a SwiftData store with a debugger and see "produce" / "dairy"; you can't with a transformable blob). The whole point of `NavigationSplitView` on iPad per CC-8 is to keep multiple surfaces visible simultaneously; sheeting away from that pattern for one feature is inconsistent. **What the iPad sidebar entry looks like:** the Saved tab's sidebar (rendered by `SavedView` in its iPad layout) renders a new "Shopping list" `Label("Shopping list", systemImage: "cart")` at the top of the sidebar list, above the saved recipe rows. Tapping selects it and the content column shows `ShoppingListView`. The detail column shows a placeholder (probably "Pick a row to see details" or similar) — but since the shopping list doesn't have a row-level detail, the detail column can stay collapsed. **Why the sidebar entry is at the TOP of the saved-recipes list and not at the bottom or as a toolbar item:** top is the canonical "navigation entry" placement (mirrors how Apple Mail's sidebar puts "Inbox" / "Drafts" / "Sent" / "Archive" above the per-mailbox listing). The same destination (`ShoppingListView`) is reached differently; that's correct adaptive navigation per CC-8. **Considered:** route the shopping list through the iPad sidebar's existing Saved-tab row as a long-press menu or contextual sub-entry. Rejected — sidebar long-press menus are non-standard on iPadOS and would surprise users. The "Shopping list" row above the saved recipes is the bog-standard pattern. **Considered:** show the shopping list inline at the top of the Saved tab's content column (above the saved recipes) as a collapsible section. Rejected — couples two surfaces (the saved-recipes list and the shopping list) into one content view, which is wrong: the shopping list has its own per-aisle structure that doesn't compose with a recipe list. They're different content shapes. **Considered:** introduce a new iPad-only "Cooking" tab that hosts both the shopping list and the saved recipes. Rejected — same argument as (b) above (top-level inflation); also forks the iPad and iPhone IA further. **Spec/trace:** US-39 / AC-39.9 (iPad split layout), CC-8 (the `NavigationSplitView` pattern). ## Phase 13 amendments (Voice Mode, 2026-05-27)

- **CL-79 (US-40 / T-690a / T-690b, 2026-05-27)** — **Cook Mode Voice Mode synthesizer, voice/locale, and audio-session decisions.** The round-3 dad "Cooking Voice Mode" backlog entry graduates as US-40, split into T-690a (the standalone `VoiceReader` core) and T-690b (the Cook Mode wiring + four App Intents + analytics). This CL resolves the four design questions the reader core raises.

  **(1) Speech engine: on-device `AVSpeechSynthesizer`, not a cloud TTS service.** **Decision: `AVSpeechSynthesizer` (AVFoundation).** The candidate alternatives were **(a) `AVSpeechSynthesizer`** — Apple's on-device text-to-speech, free, no network, no entitlement, available since iOS 7 and on both iOS and macOS; **(b) a cloud TTS API** (e.g. a server-side neural-voice service) — higher voice quality but adds a network round-trip per step, a per-character cost, a new privacy surface (step text leaves the device), and a hard dependency on connectivity *while the user is mid-recipe in a kitchen*; **(c) pre-rendered audio shipped with each recipe** — impossible, the recipe corpus is the live WordPress blog, not a fixed bundle. **Why (a):** it is the only option consistent with the backlog framing ("Uses on-device `AVSpeechSynthesizer` so no network round-trip, no subscription cost, no privacy surface") and constitution §9's "no raw user input strings to the network" posture — the step text never leaves the device. Cook Mode is used in a kitchen where connectivity is unreliable; an on-device engine keeps Voice Mode working offline (parallel to US-35's download-for-offline story). Voice quality is "good enough" — the personal-voice / enhanced-voice download is a system affordance the user controls in iOS Settings, and `AVSpeechSynthesizer` automatically picks up any enhanced voice the user has installed. **Why NOT (b):** the cost, the latency mid-step, and especially the privacy regression (sending recipe step text to a third-party TTS server) are all disqualifying for a feature whose entire selling point is "on-device, no subscription, no privacy surface." **Why NOT (c):** the corpus isn't bundled.

  **(2) Voice + locale: the system-default voice for `Locale.current`, no in-app voice picker in v1.** **Decision: resolve the voice via `AVSpeechSynthesisVoice(language:)` from the device's `Locale.current` language code (e.g. `"en-US"`), and fall back to the platform default voice when no localized voice is available.** Each utterance is an `AVSpeechUtterance` whose `.voice` is set to that resolved voice (leaving it `nil` is also acceptable — the synthesizer then uses the system default, which is the same outcome for the common case). The candidates were **(a) system-default voice for the current locale** — zero configuration, respects whatever voice + language the user has set system-wide, picks up enhanced/personal voices automatically; **(b) an in-app voice picker** — let the user choose voice + rate + pitch in a Voice Mode settings panel; **(c) a hardcoded en-US voice** — simplest but wrong for non-US-English users. **Decision: (a) for v1.** **Why (a):** it is the least-surprise default — the user's system voice setting (Settings → Accessibility → Spoken Content → Voices) is the single source of truth, so a user who has already chosen a preferred voice + speaking rate for VoiceOver / Spoken Content gets that same voice in Cook Mode for free. It also keeps the T-690a reader core free of any persisted preference. **Why NOT (b):** a per-feature voice picker duplicates an OS-level affordance, adds a settings surface + persistence + a snapshot-tested UI, and is not justified for v1 — it can graduate later if user feedback asks for an in-app rate control. **Why NOT (c):** hardcoding en-US breaks for any non-US-English device and contradicts the "respect the system" posture. **Speaking rate:** v1 uses `AVSpeechUtterance`'s default rate (`AVSpeechUtteranceDefaultSpeechRate`); no custom rate is set, so the user's system Spoken-Content rate (where it applies) and Apple's default govern pacing. A custom in-app rate slider is the natural extension if (b) is ever revisited.

  **(3) Audio session: `.playback` category + `.duckOthers` option, deactivated with `.notifyOthersOnDeactivation`.** **Decision: activate `AVAudioSession.sharedInstance()` with `category: .playback`, `mode: .default`, `options: [.duckOthers]` before the first utterance; deactivate with `.notifyOthersOnDeactivation` on `stop()`.** The candidates were **(a) `.playback` + `.duckOthers`** — the app's speech plays even when the ringer/silent switch is set to silent (correct: the user explicitly turned Voice Mode on, they want to hear it), and other audio (music, podcasts) **ducks** (drops to a low volume) for the duration of the utterance then returns to full; **(b) `.ambient`** — respects the silent switch and mixes silently with other audio, but `.ambient` would be muted by the hardware silent switch, defeating the feature when the user has their phone on silent (common in a kitchen); **(c) `.soloAmbient`** — the default category, *stops* other audio rather than ducking it — too aggressive, the user listening to a podcast while cooking would have it killed every time a step is read; **(d) `.playback` + `.mixWithOthers`** — plays over other audio at full volume without ducking, which makes the step hard to hear over loud music. **Decision: (a).** **Why `.playback`:** the user opted into Voice Mode deliberately; the step reading should be audible regardless of the silent switch, exactly as a podcast or navigation prompt is. **Why `.duckOthers` (not stop, not mix):** ducking is the polite, expected behavior for a transient spoken prompt (it mirrors turn-by-turn navigation and Siri) — the user's background music dips while the step is read, then comes back. Stopping (`.soloAmbient`) is hostile to the cook listening to music; mixing without ducking (`.mixWithOthers`) makes the step inaudible. **Why `.notifyOthersOnDeactivation` on teardown:** when Voice Mode is turned off (or the reader stops), deactivating with this option tells other apps their audio can return to full volume immediately, so the ducked podcast doesn't stay quiet. **Lifecycle:** the session is activated lazily on the *first* `speak(_:)` (not eagerly when the reader is constructed) so merely having a `VoiceReader` instance never disturbs other audio; it is deactivated on `stop()`. **Platform guard:** `AVAudioSession` is iOS-only — the activation/deactivation is wrapped in `#if os(iOS)` (mirroring the ActivityKit guard in `SystemCookLiveActivityController` per constitution §2) so the package compiles + tests on the macOS `swift test` slice. The reader's speak/stop/pause/resume state machine is exercised on both platforms via the injected mock synthesizer; only the real audio-session side-effect is compiled out on macOS.

  **(4) Testability seam + Voice-Mode-off-by-default.** **Decision: `VoiceReader` depends on a `SpeechSynthesizing` protocol (methods `speak(_:) / stop() / pause() / continueSpeaking()`, plus `isSpeaking` / `isPaused` state), with a thin adapter conforming `AVSpeechSynthesizer` to it; L1 tests inject a mock.** This mirrors the `CookLiveActivityController` protocol seam (US-11 / CL — the `SystemCookLiveActivityController` production conformance vs. the test stub) that lets `CookModeViewModel` build + test on macOS without ActivityKit. The mock records calls + flips its own `isSpeaking` / `isPaused` flags so the reader's contract — speak → speaking, stop → stopped, pause → paused, resume → speaking, and **speak-while-speaking stops the prior utterance first** (AC-40.7) — is asserted with zero real-audio dependency. **Voice-Mode-off-by-default + not-persisted (T-690b):** Voice Mode is **off** every time Cook Mode is entered and is **not** persisted across cook sessions. **Why:** an app that unexpectedly starts talking when the user opens a recipe (because they left Voice Mode on three sessions ago) is startling and potentially embarrassing (in a quiet room, on a speaker). Requiring a deliberate per-session toggle-on is the safe default; the cost is one extra tap per cook session, which is acceptable for a hands-free feature the user is consciously choosing to use. A "remember Voice Mode" preference can graduate later behind a Settings toggle if users ask. **Trace:** US-40 / AC-40.1..AC-40.8; the reader core (AC-40.2 partial, AC-40.4, AC-40.6, AC-40.7) lands in T-690a, the toggle + re-read driver + four intents + `voiceModeToggled` analytics (AC-40.1, AC-40.3, AC-40.5, AC-40.8) land in T-690b. Implementing PRs: T-690a (this CL's reader-core decisions) + T-690b (wiring + intents + analytics).

- **CL-81 (US-40 / T-690b, 2026-05-27)** — **In-app Voice Mode wiring scope: T-690b's first slice is the Cook Mode toggle + read-aloud driver + the four control methods on `CookModeViewModel`, exercised in-app and by L1 tests; the Siri App Intent exposure and the `voiceModeToggled` analytics event are deferred to a follow-up.** CL-79 split US-40 into T-690a (the standalone `VoiceReader` core) and T-690b (the full Cook Mode wiring + four `RecipeAppIntents` + `voiceModeToggled` analytics + §9 amendment). The round-8 batching note carves T-690b down to a small, completable in-app slice so the user-visible Voice Mode lands and de-risks the Siri layer: this PR ships (1) the Voice Mode toggle on `CookModeView`'s top bar per AC-40.1 (`speaker.wave.2` / `speaker.wave.2.fill`, accessibility identifier `cook-mode-voice-toggle`, label "Voice Mode", off-by-default + not-persisted per CL-79); (2) the re-read-on-step-change driver in `CookModeViewModel` per AC-40.3 — `goNext()` / `goBack()` (which the on-screen Next/Previous controls and swipe gestures already call) re-`speak(_:)` the new step whenever Voice Mode is on, including the "All done — enjoy your meal" completion line on `isFinished`; and (3) the four hands-free **control methods on the view model — `advanceStep()`, `previousStep()`, `repeatCurrentStep()`, `pauseVoice()`** — wired to `VoiceReader` and exercised in-app + by L1 tests (mock synthesizer asserts: toggle on → speaks current step, step change → re-speaks the new step, repeat → re-speaks the same step, pause → pauses, toggle off / Cook Mode exit → stops). **Why the four methods exist now but Siri is deferred:** the App Intent layer (AC-40.5) is the larger, riskier surface (App Shortcuts registration, phrase donation, targeting the active Cook Mode session through the SiriKit lifecycle). Building the view-model command surface first means the intents become a thin adapter that calls already-tested methods — the intents add SiriKit plumbing in the follow-up (**T-690c**) without re-litigating the navigation/read-aloud behavior. The methods route through the same `goNext()` / `goBack()` the on-screen controls use (AC-7.4), so a future Siri command and an on-screen tap are guaranteed identical. **What this slice does NOT include (deferred to T-690c):** the four `RecipeAppIntents` + App Shortcuts donation (AC-40.5) and the `voiceModeToggled(recipeID:enabled:)` analytics event + constitution §9 allowlist amendment (AC-40.8). The AC-40.8 §9 amendment lands paired with the event in T-690c, keeping this PR's egress surface unchanged (Voice Mode is fully on-device — no network at all) and its constitution diff empty. **AC-7.6 coverage:** `endCookMode()` calls `VoiceReader.stop()` (releasing the ducked audio session) and clears `isVoiceModeEnabled`, so exiting Cook Mode never leaves a voice reading into a closed surface — symmetric to the idle-timer + Live Activity teardown already in `endCookMode()`. **Spec/trace:** US-40 / AC-40.1 (toggle), AC-40.3 (re-read on step change), AC-40.5 (the control methods the intents will call — the in-app half only; Siri exposure is T-690c), consuming the T-690a `VoiceReader` core (AC-40.2 / AC-40.4 / AC-40.6 / AC-40.7). CL-80 was taken by T-680a's Shopping-List-logic-core split, so this Voice-Mode-wiring CL takes CL-81. Implementing PR: T-690b (`feat/T-690b-voice-wiring`); Siri intents + analytics follow-up: T-690c.

- **CL-82 (US-40 / T-690c, 2026-05-27)** — **Voice Mode Siri intents reach the live Cook Mode session through a `VoiceCommandBus` singleton (mirroring the US-10 `DeepLinkDispatcher`); the `voiceModeToggled` + `voiceCommandFired` analytics events carry only closed-set values, no free text; constitution §9 amended.** This is the Siri/analytics follow-up CL-81 deferred from T-690b. The four `CookModeViewModel` control methods (`advanceStep()` / `previousStep()` / `repeatCurrentStep()` / `pauseVoice()`) already exist and are L1-tested (T-690b); T-690c exposes them to SiriKit and adds the voice telemetry.
  **(1) How the intents reach the *live* Cook Mode view model.** The problem: an `AppIntent.perform()` runs **outside** any SwiftUI view tree and has no handle to the `@State`-owned `CookModeViewModel` that `CookModeView` constructs. US-10's `OpenRecipeIntent` solved the analogous problem for *navigation* by posting a `DeepLinkIntent` onto the `@Observable` `DeepLinkDispatcher.shared` bus that `RootView` observes; but Voice Mode commands don't navigate — they must drive the **already-presented** session's step state in place. **Decision: a new `VoiceCommandBus` singleton in `DODFeatureRecipeDetail`, mirroring the `DeepLinkDispatcher` pattern but holding a `weak var handler: (any VoiceCommandHandler)?` instead of a pending-value the root view drains.** `CookModeViewModel` conforms to `VoiceCommandHandler` (the four methods *are* the protocol); `beginCookMode()` sets `VoiceCommandBus.shared.handler = self` and `endCookMode()` clears it (`handler = nil`). Each intent's `perform()` calls `VoiceCommandBus.shared.dispatch(.next/.previous/.repeat/.pause)`; the bus's `nonisolated dispatch(_:)` hops to `@MainActor` (exactly like `DeepLinkDispatcher.dispatch`) and forwards to `handler?.advanceStep()` etc. **Why a weak handler, not a pending-command queue:** voice commands are imperative and only meaningful while Cook Mode is foreground — there is no "consume later" semantics the way a deep link is consumed once on the next render. A `weak` reference means a torn-down Cook Mode session is automatically a no-op (the handler is `nil`), and Siri firing "next step" from the lock screen with no active session does nothing rather than crashing or replaying into a stale VM. **Why the bus lives in `DODFeatureRecipeDetail`, not the App target:** the VM (which must register) lives there, and the package already depends on `DODAnalytics`; the App-target intents already `import DODFeatureRecipeDetail`, so the dependency direction is satisfied and the bus + the register/unregister wiring are L1-testable inside the package with a fake handler. **Why the intents take no `recipe` parameter** (unlike `OpenRecipeIntent`): a voice command acts on whatever step the live session is on — there is nothing to disambiguate, so the intents are parameter-less and `openAppWhenRun` is left at its default (they don't need to launch the app — if Cook Mode isn't up there's no session to drive). **(2) Phrase registration.** The four intents register on the **existing** `DODShortcuts` `AppShortcutsProvider` (US-10 / REG-10) alongside the three recipe intents — `AppShortcutsProvider` allows up to the system phrase budget and one provider per app, so we extend the existing one rather than adding a second. Phrases (each suffixed `in \(.applicationName)`): `NextStepIntent` — "next step" / "next" / "go forward"; `PreviousStepIntent` — "previous step" / "go back" / "back"; `RepeatStepIntent` — "repeat step" / "repeat that" / "say that again"; `PauseVoiceIntent` — "pause reading" / "pause". **Every utterance must contain `\(.applicationName)`** — the `appintentsmetadataprocessor` build step fails the export with "Invalid Utterance. Every App Shortcut utterance should have one '${applicationName}' in it." otherwise. This requirement applies to **all** phrases, not only those that interpolate a `@Parameter` (an earlier reading of the US-10 note had it backwards — the build error caught it); the `\(.applicationName)` token scopes the phrase to this app and Siri still matches the bare command verb once the shortcut is donated. **(3) Telemetry — two events, both closed-set, no free text (AC-40.8).** `voiceCommandFired(command:)` fires from each intent's `perform()`; `command` is a `VoiceCommandName` — a closed `String`-raw enum (`next` / `previous` / `repeat` / `pause`) — so the wire payload can only ever be one of four fixed strings, **never** the user's raw spoken phrase (which the intent layer never even sees — SiriKit matches the phrase and hands us a typed intent). `voiceModeToggled(on:)` fires from `CookModeViewModel.setVoiceMode(_:)` with a single boolean (on/off). Neither event carries a recipe id (the prior `voiceModeToggled(recipeID:enabled:)` shape sketched in CL-81 / the T-690b task entry is simplified to `voiceModeToggled(on:)` here — the recipe id adds nothing the `cookModeStarted(recipeID:)` event doesn't already capture, and dropping it keeps both Voice events to a single primitive value). **Constitution §9 allowlist amended** (US-40 authorized the Voice Mode events; this CL lands the amendment paired with the events per the "amendment lands with the event" convention): both `voiceModeToggled(on:)` and `voiceCommandFired(command:)` added as "Usage Data — Product Interaction" device-state/usage events with no free text and no PII — the App Privacy questionnaire mapping table is unchanged. **Why the command name is allowlist-safe despite being a string:** it is a fixed enum drawn from a closed set the app defines, not user input — the same posture as `widgetOpened`'s `kind` ("featured"/"saved") and `screenView`'s `name` ("feed"/"recipe_detail"), both already on the allowlist. **(4) Verification.** Siri intents can't be exercised in the sim without a device, so the verification is the per-intent L1 tests (a fake `VoiceCommandHandler` registered on the bus asserts each intent dispatches to the right method) + the analytics payload-shape tests (assert the closed enum-string set, no free text) + a clean `xcodebuild`. **PR carries the `e2e` label** per CONTRIBUTING.md (it touches App Intents). **Spec/trace:** US-40 / AC-40.5 (the four Siri intents — the in-app control surface they call landed in T-690b), AC-40.8 (`voiceModeToggled` + `voiceCommandFired` analytics + §9 amendment). CL-81 took the prior slot and T-680b is running in parallel; this CL takes the next free slot (CL-82) and the rebaser renumbers on collision. Implementing PR: T-690c (`feat/T-690c-voice-intents`).
