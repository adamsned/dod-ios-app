# Contributing to Dutch Oven Daddy iOS

Two-person team (@adamsned + @spencer0706). The workflow below is
**convention, not enforcement** — this repo is private on a free
GitHub plan, so branch protection isn't available. We trust each other
to follow these rules; CI runs on every PR so mistakes get caught
early either way.

## Golden rule

**Don't push directly to `main`.** Open a PR. Even for one-line typo
fixes — it leaves a paper trail and lets the other person see what's
landing.

The only exception is the first-bootstrap commit on this file
(adding the convention itself), since there's no PR template to use
before it exists.

## Branch naming

`<type>/<short-kebab-slug>`. Types we use:

| Prefix      | When                                                            |
|-------------|-----------------------------------------------------------------|
| `feat/`     | New user-facing capability (`feat/comments-recipe-detail`)      |
| `fix/`      | Bug fix (`fix/scroll-eaten-by-button`)                          |
| `chore/`    | Tooling, deps, CI, repo plumbing (`chore/pr-flow-setup`)        |
| `docs/`     | Spec, constitution, README, marketing copy                      |
| `test/`     | New test coverage with no behavior change                       |
| `refactor/` | Internal restructure, no behavior change                        |
| `spec/`     | Spec-driven amendment branches (`spec/comments-and-ratings`)    |

## Commit messages

[Conventional Commits](https://www.conventionalcommits.org/) — same
prefix as the branch type, scoped to the package or feature:

```
feat(detail): wire comments + ratings into RecipeDetail (US-13/14/15)
fix(persist): make test helpers visible across the schema split
chore(ci): cache SwiftLint binary between jobs
```

Reference spec/task IDs in the body when the change satisfies a
tracked item.

## Review

1. PR author requests a review from the other maintainer (CODEOWNERS
   auto-requests both, you can dismiss yourself).
2. One human approval from the *other* maintainer before merge.
3. CI must be green.
4. Squash-merge by default. Use a real merge commit only when the
   PR contains a stack of meaningful commits you want to preserve.

## What CI checks

- `lint` — SwiftLint `--strict` across every Swift package + the app
- `format-check` — `swift-format` lint on all sources
- `test-spm-matrix` — `swift test` on each Swift Package (10+)
- `test-xcode` — `xcodebuild test` on the iOS-Sim app + extensions

The `nightly-live-api` workflow runs separately on a cron and hits
the real WordPress API. Don't depend on it for PR signal.

Local pre-flight:

```bash
./scripts/format.sh                    # apply swift-format
./scripts/lint.sh                       # run SwiftLint
swift test                              # in each package you touched
xcodebuild -project DODApp.xcodeproj \
  -scheme DODApp \
  -destination 'platform=iOS Simulator,name=iPhone 17' \
  -configuration Debug build           # confirm the app target builds
```

If any of these fail locally, CI will fail too — fix before pushing.

## Working with the AI agent

When the AI agent (Claude) is doing work in this repo, it follows
the same PR rules:

1. Subagents commit on a `<type>/<slug>` branch in an isolated
   worktree.
2. The orchestrating agent pushes the branch to `origin` and
   opens a PR via `gh pr create`.
3. The agent monitors CI with `gh pr checks --watch`.
4. **Auto-merge fallback:** native auto-merge is gated behind
   GitHub Pro, so the agent simulates it by running
   `gh pr merge --squash --delete-branch` once CI reports green.
5. If CI fails, the agent fixes the issue in the same branch and
   waits for the next CI run.
6. **Human approval is still required for non-trivial PRs.** The
   agent will leave the PR open and notify you instead of
   self-merging when the change is anything beyond pure tooling,
   docs, or a confined bug fix.

If you (a human) want to override the agent and merge without
review, that's fine — the convention is for the agent's own
discipline, not a hard rule for you.

## Things that are out of scope for a PR

- Secrets, signing certs, API keys, anything in `*.xcconfig` not
  already tracked. If it shouldn't be in git, it shouldn't be in
  the PR.
- The committed `.xcodeproj` — `project.yml` is the source of
  truth; the `.xcodeproj` is gitignored and regenerated by
  XcodeGen.
- Snapshot baseline updates with no explanation. If a snapshot PNG
  changes, the PR body must explain why.

## Releasing

Versioning + TestFlight upload is a separate process documented in
`Marketing/TestFlight.md`. It runs from `main` after the PRs land,
not from a PR branch.
